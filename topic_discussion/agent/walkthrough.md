# 智能体任务问题链：从目标到可复查结果

本文跟踪一个需要查询资料并写入受控结果的任务。起点是带成功条件的任务目标，终点不是一段看似合理的文本，而是一条能够回放的轨迹：每次模型动作、工具调用、环境观察、状态变化和最终判断都可以对应。

`任务目标 → 模型动作 → 工具执行 → 环境观察 → 状态更新或重试 → 任务评测 → 采用判断`

## 单次生成为什么不足以描述任务

模型可能先选择工具、读取结果，再决定下一步动作。一次任务因此包含多个模型调用和工具调用，还可能出现超时、参数错误、无效循环和恢复。首先用[00 智能体工作负载与执行链](./00_agent_workload_and_trace.md)固定任务身份、成功条件、最大步数、模型配置和工具版本。

![Agent 从任务输入到可审计轨迹](../../docs/public/topic_discussion/agent/agent_workload_trace.svg)

## 工具反馈怎样成为可用轨迹

模型输出的工具名称和参数只表示一次动作提议。执行环境返回的状态、退出码、结构化结果和副作用，才能证明动作是否生效。[01 智能体轨迹数据与验证](./01_agent_trajectory_data.md)把任务蓝图、候选动作、环境反馈和验证结果绑定到同一轨迹，并将成功、可修复失败和不可恢复失败分开保存。

![任务蓝图、候选轨迹与验证数据](../../docs/public/topic_discussion/agent/agent_trajectory_data.svg)

## 为什么工具必须经过受控环境

训练、数据生产和评测只有在权限、依赖、资源预算与重置规则一致时才可比较。[02 智能体沙盒与执行环境](./02_agent_sandbox_environment.md)把动作提议与实际执行分开：工具接口先校验参数，沙盒再控制文件、网络、计算资源和超时，最后保存环境快照与状态差异。

![Agent 工具调用经过沙盒并产生可回放证据](../../docs/public/topic_discussion/agent/agent_sandbox_execution.svg)

## 多步任务怎样调度和恢复

每一步只有在依赖状态齐全后才能进入就绪队列；工具等待期间，其他任务可以继续模型调用，但同一轨迹不能跳过尚未返回的观察。调度记录至少区分模型队列、工具队列、沙盒等待和重试时间。请求选择与服务队列可复用[推理优化](../inference_optimization/intro.md)，任务级依赖、工具等待和上下文状态必须作为 Agent 轨迹的新增字段。

恢复不能只重发最后一次文本请求。系统需要找到最后一个已提交状态，判断工具调用是否具有副作用，并决定重试、补偿还是终止；否则可能重复写入或把旧观察绑定到新策略动作。

## 怎样同时评估质量、可靠性和成本

任务成功率回答最终目标是否完成，工具正确性回答动作是否合法且参数是否有效，轨迹质量回答是否存在无效循环或不必要步骤。延迟和成本还要拆成模型生成、工具执行、沙盒启动、网络等待和重试。上述指标必须共享任务 ID 和轨迹 ID，才能解释“质量提高但成本失控”或“延迟下降但成功率退化”。

## 什么时候需要改变协议或编排框架

先检查失败来自工具能力、参数契约、环境权限、状态依赖还是任务调度。MCP、函数调用和业务 API 解决的是工具接入问题，编排框架解决的是状态流转、并发、恢复和观测问题；两者都不能替代缺失的工具能力。只有同一批任务上的成功率、错误分布、阶段时间和资源成本已经固定，框架候选才具有可比性。

若失败来自参数不合法或返回格式不一致，优先修复工具契约；若工具等待阻塞其他任务，比较队列和并发策略；若副作用导致重试不安全，先增加幂等、补偿或提交点。框架名称本身不构成收益证据。

## 什么时候才进入 Agentic RL

先比较原始模型与经过验证的工具轨迹 SFT。如果错误主要来自工具格式、参数或观察使用，SFT 仍有直接改进空间；只有模型需要通过在线探索发现更好的多步行为，且环境能够给出稳定奖励或终态验证时，才进入 Agentic RL。
