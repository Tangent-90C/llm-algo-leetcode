# 02 · 后训练交付综合项目

> 项目类型：综合项目　项目分组：5.1 核心交付项目

## 项目定位

本项目将数据设计、监督微调（SFT）或偏好优化训练、评测、资源账本和模型产物管理组合为一次可复查的后训练交付。它回答的不是“某个损失是否下降”，而是：在给定数据、模型、预算和质量要求下，哪条后训练路径能产出值得发布、可以复现且成本可接受的模型版本。

项目以一个明确场景为输入，例如领域问答、代码助手或数学推理助手。训练方法可以从 LoRA / QLoRA 监督微调起步，再按证据决定是否进入 DPO、GRPO 或其他在线优化；不要求在一次项目中把所有算法都跑完。

## 项目问题

给定基座模型、目标任务和资源预算，建立固定基线，选择一条后训练候选路线，并形成 `accept / tune / reject` 交付决策。

至少需要明确：

- 数据：来源、许可证、任务覆盖、训练/验证/评测隔离和已知风险；
- 模型与训练：基座模型 revision、适配器或全参数策略、数据类型、优化器、学习率和有效批大小；
- 资源：单卡或多卡配置、峰值显存、训练吞吐、通信与 checkpoint 方案；
- 质量：任务正确性、指令遵循、安全/拒答、鲁棒性和行为回归；
- 产物：分词器、适配器或合并权重、配置、评测记录和回滚版本。

## 推荐项目流程

```text
定义任务与评测协议
  → 建立基座模型 / SFT 基线
  → 审核数据与训练配置
  → 训练候选模型并记录资源证据
  → 评测质量、稳定性与行为回归
  → 必要时进入偏好优化或 RL 候选
  → 比较质量增益、资源成本与产物完整性
  → 输出发布、继续调优或回滚决策
```

## 现有项目资产怎样进入综合交付

Part 02 已经分别产生数据、参数方案、SFT 基线和偏好优化候选。Part 05 不重新实现这些局部项目，而是读取它们保存的产物清单（artifact manifest）、评测和资源记录，在同一发布目标下完成跨阶段复测。

| 上游资产 | 本项目读取什么 | 进入综合比较的条件 |
|:---|:---|:---|
| [Part 02 · 64 SFT 数据质量](../02_PyTorch_Algorithms/64_SFT_Data_Quality_Project.ipynb) | 数据版本、切分、污染检查与准入状态 | 数据身份可追溯，训练与评测切分没有阻断项 |
| [Part 02 · 63 LoRA 变体](../02_PyTorch_Algorithms/63_LoRA_Variants_Benchmark.ipynb)或[Part 02 · 65 QLoRA 选型](../02_PyTorch_Algorithms/65_QLoRA_Selection_Project.ipynb) | 更新范围、适配器配置与资源依据 | 只选择一条参数方案进入正式 SFT 训练 |
| [Part 02 · 62 SFT 训练交付](../02_PyTorch_Algorithms/62_Instruction_Fine_Tuning_Project.ipynb) | 可恢复基线、分词器、适配器和固定评测 | 保存—恢复—重载一致，SFT 基线可以独立复测 |
| [Part 02 · 84 离线 DPO](../02_PyTorch_Algorithms/84_DPO_Preference_Project.ipynb)或[Part 02 · 85 GRPO / RLVR](../02_PyTorch_Algorithms/85_GRPO_Groupwise_Alignment_Project.ipynb) | 并列候选的质量、资源、失败切片和模型产物 | 候选身份完整；`reject` 保留为失败证据，不进入发布候选 |
| [Part 02 · 86 生命周期与采用决策](../02_PyTorch_Algorithms/86_DPO_Online_Benchmark.ipynb) | 策略版本、恢复、回滚和候选状态 | 生命周期证据与候选产物一致，没有无法解释的缺口 |

综合项目新增的判断是：当数据、SFT 基线和一个或多个后训练候选同时可复测时，哪一个候选在目标能力、通用能力、安全、资源成本和回滚条件之间达到发布要求。84 与 85 是并列候选分支，不是必须依次执行的训练阶段。

## 候选路线

候选路线应由任务问题和固定基线的失败模式决定，而不是按算法热度堆叠。

| 候选路线 | 适用信号 | 主要收益 | 必须一起检查的代价 |
|:---|:---|:---|:---|
| LoRA / QLoRA SFT | 格式、领域知识或指令遵循不足 | 以较低资源建立任务能力 | 验证集过拟合、数据泄漏、适配器兼容性 |
| 全参或 FSDP SFT | 小参数更新不足以修复核心能力 | 更大的适配空间 | 显存、通信、checkpoint 与训练成本 |
| DPO 等离线偏好优化 | 已有可靠 chosen / rejected 对 | 改善偏好排序与风格控制 | 数据一致性、reference 偏离、探索不足 |
| GRPO / RLVR | 任务可被规则或验证器打分 | 优化可验证推理与长链行为 | 轨迹采样成本、奖励设计、奖励投机 |
| 数据重配或清洗 | 质量回归集中在特定样本 | 先修复数据而非盲目加训练 | 覆盖面下降、分布偏移与许可证风险 |

## 小模型 Agentic RL 扩展

Agentic RL 是后训练交付的可选扩展，不是主项目的必经阶段。它检查小模型能否在受控工具环境中选择动作、读取观察、修正计划并完成任务。MiniMind 可以作为可替换的参考实现；项目判断依赖固定任务、工具协议、沙盒反馈和评测结果，不依赖某个仓库的内部文件结构。

第一版只使用结果可自动验证的工具，例如计算器、离线知识库和带单元测试的代码执行器，不接入开放互联网。训练前冻结任务集、工具 schema、沙盒限制和评分规则，再比较以下候选：

| 实验组 | 训练状态 | 要回答的问题 |
|:---|:---|:---|
| G0 · 原始基线 | 未进行工具轨迹训练 | 模型原本能够完成多少任务，主要失败发生在哪里？ |
| G1 · 工具轨迹 SFT | 学习经过验证的成功轨迹 | 示范学习能否建立正确的工具选择、参数和观察使用方式？ |
| G2 · SFT + Agentic RL | 当前策略采样并根据环境反馈更新 | 在线探索是否带来超出 SFT 的任务增益？ |
| G3 · 奖励或工具消融 | 移除一项奖励分量或工具能力 | 增益来自任务能力、奖励漏洞，还是某个工具捷径？ |

四组实验共用冻结任务、工具 schema、沙盒限制和评分规则。每条轨迹保存任务身份、策略版本、动作、工具参数、环境观察、奖励分量、终止原因和消费状态；采用决策读取任务成功率、工具正确性、失败后重规划、安全回归、采样成本和回滚证据，不用奖励总分单独决定发布。当这些输入和结果能够独立复测时，再建立单独的 Agentic RL 综合项目。

## 证据要求

### 工作负载、训练与产物

所有基线与候选都要保存同一套可复现实验信息：数据版本与切分、模型 revision、随机种子、训练配置、硬件与软件版本。适配器、合并权重、分词器和评测配置应有可定位的产物清单；只有损失曲线而没有这些信息，无法构成交付证据。

### 核心指标

| 证据类别 | 最少记录的指标 | 用途 |
|:---|:---|:---|
| 数据质量 | 去重率、格式通过率、难度/来源分布、泄漏检查 | 判断训练信号是否可信 |
| 训练过程 | train/validation loss、有效 batch、tokens/s、峰值显存、稳定性 | 判断是否学到目标而非只消耗资源 |
| 任务质量 | 正确性、指令遵循、格式通过率、win-rate 或 rubric score | 判断能力是否达到场景要求 |
| 对齐与风险 | 安全、拒答、鲁棒性、行为回归、奖励投机信号 | 判断质量增益是否带来不可接受风险 |
| 系统成本 | GPU 时间、通信等待、checkpoint 体积、单位样本/Token 成本 | 判断方案能否稳定复跑与扩展 |
| 交付完整性 | 产物清单、环境配置、评测报告、回滚版本 | 判断模型是否可以发布和追溯 |

## 最终交付物

1. 一份任务、数据来源、许可证与评测协议说明；
2. 一份基线 / 候选训练配置与资源账本；
3. 一份质量、对齐与失败案例对照表；
4. 一份模型产物清单，包含分词器、适配器 / 权重、配置和版本；
5. 一份训练与评测的失败记录、复测入口和成本估算；
6. 一项明确的 `accept / tune / reject` 发布决策，以及下一轮数据、训练或系统改进方向。
